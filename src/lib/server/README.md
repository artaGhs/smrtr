# Generation backend

`POST /api/generate` accepts `{requestId, text}` and returns the shared validated `{requestId, lesson}` response. `Accept: application/x-ndjson` opts into complete JSON-line events: a validated concept plan, individually validated modules as they finish, then a fully validated final lesson. Stream errors use the shared error event. JSON errors have non-2xx status and `{error, code}`.

The model creates an input-specific plan and independently creates each concept module, with at most three module requests in flight. Each stage gets one repair attempt for invalid structure/references. Source records and lesson/revision IDs come from the server. Original submitted text is preserved exactly; only the provider's prompt copy normalizes line endings and surrounding whitespace. Every concept/module references that source, meaning it was derived from the supplied topic, not that the source proves every generated elaboration. No generated external links are accepted. No sample lesson is returned by this endpoint.

New provider plans also require `teachingPlan`: a concrete opening question, the big-picture purpose, and a deliberate sequence of example/visual/explanation/practice approaches with a specific purpose for each concept. This sequence is independent of prerequisite order and concept relationships; an accessible application can introduce the pattern before its underlying abstraction. Module generation receives the actual teaching step, purpose and position, schedules in teaching order, and returns modules in that order. Prerequisite paths remain separately checked. The model is instructed to make the approach affect the worked example, explanation, activity and questions rather than attach labels to a definition-first lecture. Validation checks unique complete concept coverage and meaningful bounded text. Existing lessons without metadata remain accepted; MCP exports include the optional schema field and request this strategy for newly authored lessons.

The provider interface in `provider.ts` is injectable; OpenRouter is selected when server-only `OPENROUTER_API_KEY` is set, with `SMRTR_OPENROUTER_MODEL` defaulting to `openai/gpt-4.1`, strict JSON schema output, and compatible endpoint routing. Otherwise the existing OpenAI Responses adapter uses strict structured outputs and `store:false`. Set server-only `OPENAI_API_KEY`, optional `SMRTR_MODEL` (default `gpt-4.1`), and optional `SMRTR_GENERATION_TIMEOUT_MS` (default 120000, bounded to 1000–180000). Never use a public/client environment variable for the key. Missing key is `PROVIDER_NOT_CONFIGURED`. Provider auth, quota, unavailable, refusal, incomplete, timeout and invalid-output errors are sanitized before returning to clients. Canceling requests aborts provider calls; the first failed worker cancels remaining work.

Validation covers schema shape, unique IDs, source/concept/question references, connected maps, complete learning paths, prerequisite order, module coverage, option answer sets and bounded graph inputs. General related/contrast/example cycles are valid. BFS practice uses the shared simulation core, with ASCII alphabetical neighbor IDs and visited-on-enqueue; the server replaces model-authored BFS activity answer keys with computed traversal and minimum-edge/unreachable questions. Other conceptual content remains model generated; structural checks do not prove factual correctness. Final practice reuses generated retrieval questions with distinct IDs and adds fresh computed BFS distance questions.

Tests run through `npm test` and `npm run typecheck`. Mock provider and mocked HTTP tests cover distinct input topics, progressive delivery before all modules finish, original sources, repair limits, abort/timeout, error sanitization and schema compatibility. These tests make no live provider requests. Live verification requires a configured server key and should be reported separately.

Provider documentation: [Responses structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses), [GPT-4.1](https://developers.openai.com/api/docs/models/gpt-4.1).

## Keyless connected chat

`chat-store.ts` supports a separate workflow that needs no provider API key. The browser creates a request with `POST /api/chat/requests {requestId?,text}`. It receives a random ID and polls `GET /api/chat/requests/[id]`. A local stdio MCP client, current coding chat using the exported store functions, or a user copying the JSON export can author a fresh complete lesson from that exact request. Browser status remains `waiting` until a validated lesson is submitted; this does not call or grant access to a user's chat subscription automatically.

`GET /api/chat/requests/[id]/export` returns trusted task instructions, the untrusted original notes, exact required metadata and the lesson JSON schema. `POST /api/chat/requests/[id]/lesson {lesson,revision?}` accepts a complete lesson. Revision defaults to `lesson.revision` and must match the exported request. Browser JSON import must therefore retain the exported revision. `DELETE /api/chat/requests/[id]` cancels pending work. There is no web endpoint listing other requests; local MCP lists pending summaries through the shared store.

The store location defaults to `.smrtr/requests` in the app working directory, or `SMRTR_BRIDGE_DIR`. The app and MCP process must use the same directory. The directory contains private runtime source text and must remain ignored by Git; the integrator owns this ignore configuration. New files use mode 0600 and atomic write/rename; filesystem locks serialize writes from separate processes. Requests expire after 24 hours. Canceled, completed, failed, expired or mismatched revisions reject late submissions. Invalid lessons remain pending for correction; explicit chat failure can use `failChatRequest`. Inputs are capped at 40,000 characters, persisted lesson/request files at 1.5 MB. No arbitrary generated code executes and no sample is substituted.

Shared exports are `createChatRequest`, `listPendingChatRequests`, `getChatRequest`, `submitChatLesson`, `cancelChatRequest`, `failChatRequest`, and `getChatGenerationInstructions`. Optional `{directory,now}` overrides support isolated tests. MCP uses local stdio and direct file-store access; this backend does not create a public remote MCP listener.

## Hierarchy and fixed learner confidence

New requests accept `learnerProfile: {overall, topics:[{id,label,level}]}` with self-reported levels `new`, `recognize`, `explain`, `apply`. A null topic level inherits overall; IDs must be unique and stay stable across requests. Creation normalizes and stores a private version-2 request snapshot, visible in the public pending response and MCP export. Submitted lesson metadata cannot replace it. Version-1 stored requests remain readable and may accept legacy lessons without new authored structure. New version-2 requests require an authored `teachingPlan` and `learningDesign`; the backend never invents those fields from an old saved lesson.

`learningDesign` separates the page containment hierarchy, main instructional sequence and cyclic concept relationships. It states the central question, objective and assumed knowledge; one continuing scenario has stable entities and optional canonical activity inputs. Pages contain bounded paragraph/callout blocks with stable unique block IDs, prose and contextual links with explanatory reasons. Support pages can nest (Queue → FIFO) and link back cyclically, while page parent references must form one acyclic hierarchy rooted at an overview page. Support pages stay outside the main sequence and confidence routes. The novice route covers the complete main progression; experienced routes change emphasis and may begin at why/transfer rather than repeat definitions.

Provider plans must author this design and meaningful relation explanations. Profile and confidence guidance are included in every provider request. Per-concept module context includes relevant pages, selected confidence route and effective topic confidence: explicit topic levels take priority, null inherits overall, and multiple relevant topics use the least confident report for scaffolding. This changes requested examples, language, mechanism depth and transfer work; it is not a mastery diagnosis. All core/support graph views must bind the canonical scenario activity, and its module must preserve exact inputs. A transfer page may explicitly bind a different existing algorithm module with a labeled generated example. BFS questions for both are still computed with the shared simulator.

Validation checks all page/concept/source/topic references, globally unique block IDs for exact return context, bounded link reasons/transitions, complete main sequence, routes and canonical activity agreement. It does not claim to prove the factual correctness or teaching quality of arbitrary prose. Tests cover profile snapshots and attempted overwrite, legacy imports, distinct novice/apply guidance, support-link cycles versus parent cycles, graph mismatch repair, transfer exceptions and API export before fulfillment.

When a lesson has `learningDesign`, every concept relation must also carry explanatory `meaning`: 12–500 characters describing how the connection helps understanding, with empty values and bare relationship labels rejected. This applies equally to provider generation and chat/MCP import; invalid chat submissions remain pending for correction. Older lessons without a learning design retain optional relation meaning.
