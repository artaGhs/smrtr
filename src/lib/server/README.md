# Generation backend

`POST /api/generate` accepts `{requestId, text}` and returns the shared validated `{requestId, lesson}` response. `Accept: application/x-ndjson` opts into complete JSON-line events: a validated concept plan, individually validated modules as they finish, then a fully validated final lesson. Stream errors use the shared error event. JSON errors have non-2xx status and `{error, code}`.

The model creates an input-specific plan and independently creates each concept module, with at most three module requests in flight. Each stage gets one repair attempt for invalid structure/references. Source records and lesson/revision IDs come from the server. Original submitted text is preserved exactly; only the provider's prompt copy normalizes line endings and surrounding whitespace. Every concept/module references that source, meaning it was derived from the supplied topic, not that the source proves every generated elaboration. No generated external links are accepted. No sample lesson is returned by this endpoint.

The provider interface in `provider.ts` is injectable; the current implementation uses OpenAI Responses with strict structured outputs and `store:false`. Set server-only `OPENAI_API_KEY`, optional `SMRTR_MODEL` (default `gpt-4.1`), and optional `SMRTR_GENERATION_TIMEOUT_MS` (default 120000, bounded to 1000–180000). Never use a public/client environment variable for the key. Missing key is `PROVIDER_NOT_CONFIGURED`. Provider auth, quota, unavailable, refusal, incomplete, timeout and invalid-output errors are sanitized before returning to clients. Canceling requests aborts provider calls; the first failed worker cancels remaining work.

Validation covers schema shape, unique IDs, source/concept/question references, connected maps, complete learning paths, prerequisite order, module coverage, option answer sets and bounded graph inputs. General related/contrast/example cycles are valid. BFS practice uses the shared simulation core, with ASCII alphabetical neighbor IDs and visited-on-enqueue; the server replaces model-authored BFS activity answer keys with computed traversal and minimum-edge/unreachable questions. Other conceptual content remains model generated; structural checks do not prove factual correctness. Final practice reuses generated retrieval questions with distinct IDs and adds fresh computed BFS distance questions.

Tests run through `npm test` and `npm run typecheck`. Mock provider and mocked HTTP tests cover distinct input topics, progressive delivery before all modules finish, original sources, repair limits, abort/timeout, error sanitization and schema compatibility. These tests make no live provider requests. Live verification requires a configured server key and should be reported separately.

Provider documentation: [Responses structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses), [GPT-4.1](https://developers.openai.com/api/docs/models/gpt-4.1).

## Keyless connected chat

`chat-store.ts` supports a separate workflow that needs no provider API key. The browser creates a request with `POST /api/chat/requests {requestId?,text}`. It receives a random ID and polls `GET /api/chat/requests/[id]`. A local stdio MCP client, current coding chat using the exported store functions, or a user copying the JSON export can author a fresh complete lesson from that exact request. Browser status remains `waiting` until a validated lesson is submitted; this does not call or grant access to a user's chat subscription automatically.

`GET /api/chat/requests/[id]/export` returns trusted task instructions, the untrusted original notes, exact required metadata and the lesson JSON schema. `POST /api/chat/requests/[id]/lesson {lesson,revision?}` accepts a complete lesson. Revision defaults to `lesson.revision` and must match the exported request. Browser JSON import must therefore retain the exported revision. `DELETE /api/chat/requests/[id]` cancels pending work. There is no web endpoint listing other requests; local MCP lists pending summaries through the shared store.

The store location defaults to `.smrtr/requests` in the app working directory, or `SMRTR_BRIDGE_DIR`. The app and MCP process must use the same directory. The directory contains private runtime source text and must remain ignored by Git; the integrator owns this ignore configuration. New files use mode 0600 and atomic write/rename; filesystem locks serialize writes from separate processes. Requests expire after 24 hours. Canceled, completed, failed, expired or mismatched revisions reject late submissions. Invalid lessons remain pending for correction; explicit chat failure can use `failChatRequest`. Inputs are capped at 40,000 characters, persisted lesson/request files at 1.5 MB. No arbitrary generated code executes and no sample is substituted.

Shared exports are `createChatRequest`, `listPendingChatRequests`, `getChatRequest`, `submitChatLesson`, `cancelChatRequest`, `failChatRequest`, and `getChatGenerationInstructions`. Optional `{directory,now}` overrides support isolated tests. MCP uses local stdio and direct file-store access; this backend does not create a public remote MCP listener.
